# 3. `back/events.go` — мгновенные сообщения

[← Оглавление](README.md)

Этот файл делает так, что получатель видит новое сообщение **сразу**, без обновления страницы.

## Идея: «долгий опрос» (long polling)

```
Браузер получателя                         Сервер                         Браузер отправителя
       │  GET /api/events?after=K-41          │                                    │
       │ ───────────────────────────────────► │  (событий после 41 нет —           │
       │                                      │   ждём, ответ не отправляем)       │
       │                                      │                                    │
       │                                      │ ◄───── POST /api/chats/5/messages ─│
       │                                      │  sendMessage → publish(событие 42) │
       │                                      │  ── будит всех ждущих ──           │
       │ ◄─────────────────────────────────── │                                    │
       │  {cursor:"K-42", events:[...]}       │                                    │
       │  (сообщение рисуется на экране)      │                                    │
       │  GET /api/events?after=K-42          │                                    │
       │ ───────────────────────────────────► │  снова ждём…                       │
```

1. Сайт спрашивает «что нового после события №41?».
2. Нового нет — сервер **не отвечает** и держит запрос открытым (до 25 секунд).
3. Кто-то пишет сообщение → `publish` будит все ждущие запросы → каждый смотрит, есть ли новое событие для **своего** пользователя, и если есть — сразу отвечает.
4. Сайт рисует сообщение и тут же задаёт следующий вопрос.
5. Если за 25 секунд ничего не случилось — сервер отвечает пустым списком, сайт спрашивает снова.

Так у каждой открытой вкладки почти всегда «висит» вопрос к серверу, и событие доходит за доли секунды.

### Почему не «поток» (SSE / WebSocket)

Поток — это ответ, который не заканчивается, а сервер дописывает в него события. Такой ответ по дороге может «придержать» антивирус (веб-защита Касперского, ESET и т.п.), корпоративный прокси или туннель: они отдают ответ браузеру, только когда он закончился. В итоге сообщение не доходит, пока не обновишь страницу. Ответ долгого опроса — обычный законченный JSON, поэтому проходит где угодно.

### Зачем курсор

У каждого события есть порядковый номер `seq`. Сайт присылает номер последнего события, которое уже получил, и сервер отдаёт **всё**, что было после него. Поэтому даже если между двумя вопросами прошло несколько секунд (или пропала связь), ни одно сообщение не потеряется.

## Константы

```go
const pollWait = 25 * time.Second
```
Сколько сервер ждёт событий, прежде чем ответить пустым списком. Это дольше общего тайм-аута ответа (10 секунд в `main.go`), поэтому обработчик продлевает себе тайм-аут. Больше 30 секунд лучше не ставить: некоторые прокси обрывают запросы, на которые долго нет ответа.

```go
const keepEvents = 500
```
Сколько последних событий сервер помнит. Если вкладка отстала сильнее (компьютер «спал»), она получит `resync: true` и перечитает чаты целиком.

## Тип `storedEvent`

```go
type storedEvent struct {
	seq     int64
	allowed func(user map[string]any) bool // nil — всем
	data    map[string]any
}
```
Одно событие:
- `seq` — порядковый номер (1, 2, 3, …);
- `allowed` — функция «можно ли этому пользователю показать событие». Для сообщения из чата это `canSeeChat(пользователь, чат)`, для клуба — `nil` (всем);
- `data` — то, что уйдёт браузеру, например `{"type": "message", "chatId": 5, "message": {...}}`.

## Общие переменные

```go
var (
	eventsMutex sync.Mutex
	eventLog    []storedEvent
	lastSeq     int64
	newEvent    = make(chan struct{})
	kicked      = map[any]chan struct{}{}
	bootID      = strconv.FormatInt(time.Now().UnixNano(), 36)
)
```
| Переменная | Что хранит |
|---|---|
| `eventsMutex` | «замок» для всех переменных ниже: их читают и меняют одновременно разные запросы |
| `eventLog` | последние 500 событий по возрастанию `seq` |
| `lastSeq` | номер последнего события |
| `newEvent` | **канал-звонок**. Ждущие запросы «слушают» его; `publish` закрывает канал — и все слушатели просыпаются разом. Сразу после этого создаётся новый канал для следующих ожиданий |
| `kicked` | id пользователя → канал, закрытие которого обрывает его ожидание. Нужен для блокировки (`disconnect`) |
| `bootID` | «номер запуска» сервера — текущее время в наносекундах, записанное буквами и цифрами (основание 36). После перезапуска сервера номера событий начинаются заново с 1; по `bootID` в курсоре сайт и сервер поймут, что старый курсор не годится |

> **Как работает «звонок» на канале.** В Go чтение из канала (`<-wake`) ждёт, пока в канал что-то не положат **или** пока его не закроют. Закрытие будит **всех** читателей сразу. Поэтому один `close(newEvent)` будит сколько угодно ждущих запросов.

## `publish(data, allowed)`

```go
eventsMutex.Lock()
defer eventsMutex.Unlock()

lastSeq++
eventLog = append(eventLog, storedEvent{seq: lastSeq, allowed: allowed, data: data})
if len(eventLog) > keepEvents {
	eventLog = eventLog[len(eventLog)-keepEvents:]
}

close(newEvent)
newEvent = make(chan struct{})
```
1. Берём замок (и отпустим при выходе — `defer`).
2. Новый номер события и запись в журнал.
3. Если в журнале больше 500 событий — отрезаем самые старые.
4. «Звоним»: закрываем канал — все ждущие запросы просыпаются.
5. Ставим новый канал для следующих ожиданий.

Вызывается из `sendMessage` (сообщение в чат) и `sendClubMessage` (сообщение в клуб) в `api.go`.

## `disconnect(userID)`

```go
if ch, found := kicked[userID]; found {
	close(ch)
	delete(kicked, userID)
}
```
Если пользователь сейчас ждёт событий — закрываем его канал: ожидание прерывается, запрос отвечает пустым списком. Следующий запрос сайта получит `401` (сессии удалены в `blockUser`), и сайт перестанет спрашивать. Вызывается из `blockUser`.

## `cursor(seq)` и `parseCursor(text)`

```go
func cursor(seq int64) string {
	return bootID + "-" + strconv.FormatInt(seq, 10)
}
```
Курсор для сайта: `"<номер запуска>-<номер события>"`, например `"lq3x9k2a-42"`.

```go
func parseCursor(text string) (seq int64, ok bool) {
	boot, number, found := strings.Cut(text, "-")
	if !found || boot != bootID {
		return 0, false
	}
	seq, err := strconv.ParseInt(number, 10, 64)
	if err != nil || seq < 0 || seq > lastSeq {
		return 0, false
	}
	return seq, true
}
```
1. `strings.Cut` делит строку по первому `-`.
2. Нет `-` или курсор от **другого запуска** сервера → не годится.
3. Номер не число, отрицательный или больше последнего события (испорчен) → не годится.

## `events` — `GET /api/events?after=<курсор>`

Ответ: `{cursor, events, resync}`.

### Подготовка
```go
rc := http.NewResponseController(w)
rc.SetReadDeadline(time.Time{})
rc.SetWriteDeadline(time.Now().Add(pollWait + 10*time.Second))
w.Header().Set("Cache-Control", "no-store")
```
- `ResponseController` позволяет поменять тайм-ауты **только для этого запроса**.
- Тайм-аут чтения снимаем (`time.Time{}` — «без срока»): иначе через 10 секунд сервер посчитал бы соединение оборванным.
- Тайм-аут ответа продлеваем до 35 секунд — с запасом к 25 секундам ожидания.
- `Cache-Control: no-store` — ответ нельзя брать из кэша: он каждый раз новый.

```go
after := r.URL.Query().Get("after")
timeout := time.NewTimer(pollWait)
defer timeout.Stop()
```
Курсор из адреса и таймер на 25 секунд (останавливается при выходе, чтобы не висеть в памяти).

### Цикл
```go
for {
	eventsMutex.Lock()
```
Каждый круг начинается с замка: читаем общие переменные.

**Самый первый вопрос (без `after`):**
```go
if after == "" {
	eventsMutex.Unlock()
	return send(w, 200, {"cursor": cursor(lastSeq), "events": [], "resync": false})
}
```
Сразу отвечаем текущим курсором: «с этого момента следи за новым». Старые события новой вкладке не нужны — всё старое она и так загрузила через `/api/data`.

**Курсор не подошёл:**
```go
seq, ok := parseCursor(after)
oldest := lastSeq - int64(len(eventLog))
if !ok || seq < oldest {
	... return send(..., "resync": true)
}
```
`oldest` — номер, до которого события уже забыты. Если курсор от старого запуска сервера, испорчен или вкладка отстала дальше, чем помнит журнал, — отвечаем `resync: true` и текущим курсором. Сайт перечитает список чатов и открытый чат.

**Собираем события для этого пользователя:**
```go
found := []any{}
for _, e := range eventLog {
	if e.seq > seq && (e.allowed == nil || e.allowed(user)) {
		found = append(found, e.data)
	}
}
```
Только события **после** курсора и только те, что этому пользователю можно видеть. Например, преподаватель не получит событие из чата группы, а посторонний — из чужой лички.

**Запоминаем, чего ждать, и отпускаем замок:**
```go
current := lastSeq
wake := newEvent
kick := kicked[user["id"]]
if kick == nil {
	kick = make(chan struct{})
	kicked[user["id"]] = kick
}
eventsMutex.Unlock()
```
`wake` — текущий канал-звонок. Его нужно взять **под замком**, иначе можно проспать событие, случившееся между проверкой журнала и началом ожидания. `kick` — канал для блокировки этого пользователя (общий для всех его вкладок).

**Есть события — отвечаем сразу:**
```go
if len(found) > 0 {
	return send(w, 200, {"cursor": cursor(current), "events": found, "resync": false})
}
```

**Событий нет — ждём:**
```go
after = cursor(current)
select {
case <-wake:
case <-timeout.C:
	return send(..., "events": [] ...)
case <-kick:
	return send(..., "events": [] ...)
case <-r.Context().Done():
	return nil
}
```
- Сначала сдвигаем курсор до `current`: если в журнале были события, но **не для нас**, на следующем круге не перебираем их заново.
- `select` ждёт, что случится раньше:
  - **звонок** (`wake`) — появилось новое событие → идём на новый круг цикла и смотрим, наше ли оно;
  - **25 секунд** прошли → пустой ответ, сайт спросит снова;
  - **пользователя заблокировали** (`kick`) → пустой ответ, следующий запрос получит 401;
  - **вкладку закрыли или обновили** (`r.Context().Done()`) → отвечать некому, просто выходим.

### Пример ответа
```json
{
  "cursor": "lq3x9k2a-42",
  "events": [
    {"type": "message", "chatId": 5,
     "message": {"id": 812, "userId": 6, "text": "Привет", "time": "12:05", "reactions": []}},
    {"type": "club", "clubId": "1"}
  ],
  "resync": false
}
```

## Нагрузка

Каждая открытая вкладка держит один запрос. Пока событий нет, такой запрос ничего не делает и почти не тратит ресурсы (горутина Go весит несколько килобайт). При новом событии просыпаются все ждущие запросы, но каждый только перебирает журнал в памяти — для учебного проекта на сотни пользователей этого с запасом хватает.
