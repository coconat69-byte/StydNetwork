## 1. Что это за проект

СтудСеть — учебная закрытая соцсеть колледжа. В ней есть:

- вход по личному коду доступа (свободной регистрации нет);
- чаты: каналы с объявлениями, чаты групп, направлений, курсов, флудилка и личные сообщения;
- поиск людей с фильтрами;
- клубы по интересам со своими чатами;
- профиль и настройки (тема, уведомления, приватность);
- админ-панель: каналы, объявления, пользователи, жалобы.

Сайт работает в двух режимах:

1. **С сервером.** В папке `back` запускается `go run .`. Данные лежат в базе SQLite (`back/studnet.db`) и сохраняются навсегда.
2. **Без сервера.** Просто открываете `index.html`. Данные берутся из `js/data.js`, изменения живут до обновления страницы.

Сайт сам выбирает режим: сначала пробует сервер, а если тот не отвечает — переключается на `data.js`.

Коды для входа:

| Код | Кто |
|---|---|
| `123-123-123` | студент Яша Кузнецов |
| `456-456-456` | преподаватель и администратор Ольга Сидорова |
| `789-789-789` | преподаватель Артём Досиксов |

## 2. Как запустить

**С сервером** (нужен [Go](https://go.dev/dl/) версии 1.22 или новее):

```bash
cd back
go run .
```

Откройте http://localhost:8080.

**Без сервера:** откройте `index.html` двойным щелчком или через Live Server.

**Сбросить базу к стартовым данным:** остановите сервер, удалите `back/studnet.db`, запустите снова.

## 4. Как всё работает вместе (общая схема)

```
 Браузер                                         Сервер (back/)
┌─────────────────────────────┐   fetch /api/…   ┌──────────────────────┐
│ app.js  — рисует экраны     │ ───────────────► │ main.go — адреса     │
│    │                        │                  │ api.go  — обработчики│
│    ▼                        │ ◄─────────────── │ db.go   — запросы    │
│ api.js  — API.что-то()      │    JSON-ответ    │    │                 │
│    │  сервер не отвечает?   │                  │    ▼                 │
│    ▼                        │                  │ studnet.db (SQLite)  │
│ LOCAL — то же, но в памяти  │                  └──────────────────────┘
│    ▲                        │
│ data.js — MOCK_DATA         │
└─────────────────────────────┘
```

1. `app.js` никогда не лезет в данные напрямую. Ему нужны сообщения — он вызывает `API.messages(id)`.
2. `api.js` отправляет запрос на сервер. Если сервер не запущен — выполняет то же действие у себя, в объекте `LOCAL`, с данными из `data.js`.
3. Сервер проверяет, кто спрашивает (по токену), достаёт данные из базы и отвечает JSON-ом.
4. `app.js` получает данные и перерисовывает нужную часть экрана.

## 5. Фронтенд: `index.html` и `js/theme.js`

`index.html` содержит разметку **всех** экранов сразу. Экраны — это теги `<section class="screen" id="screen-…">`. Виден только тот, у которого есть класс `is-active` (его ставит функция `navigate` в `app.js`).

Части экранов, которые зависят от данных (список чатов, карточки людей, профиль), в HTML пустые — их заполняет `app.js`.

Порядок скриптов важен:

1. `js/theme.js` — в `<head>`, **до** стилей. Ставит тему (`light` / `dark`) из `localStorage` и, если в этой вкладке уже входили (есть токен в `sessionStorage`), добавляет на `<html>` класс `logged-in`. Благодаря этому при обновлении страницы не мелькает ни белый фон в тёмной теме, ни форма входа.
2. В конце `<body>`: `data.js` → `api.js` → `app.js`. Каждый следующий пользуется предыдущим.

Почему `theme.js` — отдельный файл, а не `<script>` прямо в HTML: сервер запрещает встроенные скрипты (см. раздел «Безопасность», CSP). Так даже если злоумышленник вставит `<script>` в страницу, браузер его не выполнит.

### Когда нужен код доступа

| Действие | Нужен код? |
|---|---|
| Первый заход / новая вкладка | да |
| Обновление страницы (F5) | нет, токен лежит в `sessionStorage` |
| Закрыли вкладку и открыли снова | да, `sessionStorage` стёрся |
| Кнопка «Выйти» в настройках | да, токен удаляется |
| Прошло 7 дней (режим с сервером) | да, токен просрочен |

Тема хранится в `localStorage` (`studnet-theme`) и не сбрасывается при закрытии вкладки.

## 6. Фронтенд: `js/data.js` — данные

Файл выглядит как `const MOCK_DATA = { ... };`, а внутри фигурных скобок — **чистый JSON**: кавычки только двойные, без комментариев и запятых в конце. Это нужно потому, что сервер при создании базы вырезает текст от первой `{` до последней `}` и читает его как JSON.

| Поле | Что в нём |
|---|---|
| `accessCodes` | код `"123-123-123"` → id пользователя |
| `groups`, `directions` | списки для фильтров поиска |
| `users` | люди: имя, почта, фото, группа, курс, роль (`student` / `teacher`), интересы, `bio`. У администратора ещё `isAdmin: true` |
| `chatTypes` | типы чатов и их подписи. `readonly: true` — писать могут только преподаватели (каналы) |
| `chats` | чаты. У личных (`type: "dm"`) нет названия, зато есть `ownerId` и `userId` — двое собеседников |
| `messages` | id чата → список сообщений |
| `clubs` | клубы, `memberIds` — id участников |
| `clubMessages` | id клуба → сообщения чата клуба |
| `reports` | жалобы для вкладки «Модерация» |

Менять стартовые данные нужно **только здесь**. Если сервер уже запускали, удалите `back/studnet.db` — при следующем запуске база заполнится заново.

## 7. Фронтенд: `js/api.js` — откуда брать данные

### Объект `API`

Единственная «дверь» между интерфейсом и данными. У каждого действия свой метод: `API.login(code)`, `API.messages(chatId)`, `API.sendMessage(chatId, text)` и т.д. — полный список совпадает с адресами сервера (раздел 11).

Главные служебные функции:

- **`API.request(path, body)`** — один запрос к серверу через `fetch`. Есть `body` — это POST, нет — GET. Добавляет заголовок `Authorization: Bearer <токен>`. Различает два вида проблем:
  - сервер вообще не ответил → ошибка с пометкой `offline` (значит, сервера нет);
  - сервер ответил ошибкой → обычная ошибка с текстом от сервера (например, «Неверный код доступа»), её покажут человеку.
- **`API.call(сСервера, безСервера)`** — пробует первую функцию. Если сервер не найден с самого начала, ставит `API.offline = true` и с этого момента всегда вызывает вторую (под шапкой появляется красная плашка «Сервер не найден»). Если же сервер уже отвечал, а потом пропал (его перезапускают, пропала сеть), режим без сервера **не** включается: человек видит ошибку «Нет связи с сервером». Иначе сообщение «отправилось» бы только на экране и пропало после обновления страницы.

Адрес сервера ищет `API.findServer` при первом запросе: спрашивает `/api/me` по очереди
1) там же, откуда открыта страница (её отдал сам сервер — `localhost:8080`, адрес компьютера в сети, туннель);
2) на том же компьютере, порт 8080 (Live Server — в том числе с телефона по адресу вида `192.168.1.5:5500`);
3) `http://localhost:8080` (`index.html` открыт двойным щелчком).

Подходит первый адрес, который ответил JSON-ом (так отвечает только наш сервер).

### Объект `LOCAL`

Повторяет действия сервера, но в памяти браузера, с данными из `MOCK_DATA`: вход по коду, отправка сообщения, вступление в клуб, блокировка и т.д. Повторяет и проверки сервера (например, менять можно только разрешённые настройки, в каналы пишут только преподаватели).

Токен в режиме без сервера — строка вида `local-1`, где `1` — id пользователя.

> Режим без сервера — только для демонстрации. Все данные лежат в браузере, и любой может поменять их через консоль. Настоящая защита есть только в режиме с сервером.

## 8. Фронтенд: `js/app.js` — интерфейс

Весь файл обёрнут в `(function () { ... })();` — так его переменные не мешают другим скриптам.

### Данные и состояние

- **`DATA`** — все данные после входа: пользователи, чаты, клубы, типы чатов.
- **`state`** — где сейчас человек: экран, открытый чат, клуб, вкладки. При уходе со страницы (`pagehide`) сохраняется в `sessionStorage` (`saveState`), а после входа восстанавливается (`restoreState`). Поэтому после F5 вы остаётесь в том же чате.

### Помощники

| Функция | Что делает |
|---|---|
| `$('#id')` | найти элемент на странице |
| `esc(текст)` | **защита от XSS**: заменяет `& < > " '` на безопасные коды (`&lt;` и т.п.) |
| `userById`, `chatById`, `clubById` | найти объект по id |
| `setting(user, key)` | включена ли настройка (с учётом значения по умолчанию) |
| `canMessage(user)` | можно ли написать человеку |
| `plural(n, …)`, `membersText(n)` | «1 участник», «3 участника», «25 участников» |
| `avatar`, `dot`, `about`, `tags` | готовые куски HTML для людей |
| `markTab(блок, атрибут, значение)` | подсветить активную кнопку-вкладку |
| `onClick(блок, атрибут, функция)` | один обработчик кликов на весь блок (см. ниже) |

**Как работают клики.** Почти все кнопки рисуются кодом, поэтому вешать обработчик на каждую неудобно. Вместо этого у кнопки есть атрибут, например `data-chat="5"`, а обработчик висит на всём блоке (`onClick($('#chat-list'), 'chat', openChat)`). При клике он ищет ближайший элемент с `data-chat` и вызывает функцию с его значением. Так работают даже кнопки, нарисованные позже. Все обработчики вешаются один раз в `bindEvents()`.

### Как рисуется экран

Функции `render…()` собирают HTML-строку с помощью шаблонных строк (`` `...${значение}...` ``) и кладут её в `innerHTML`. **Каждое** значение из данных проходит через `esc(...)` — см. раздел «Безопасность».

### Запуск и вход

1. `DOMContentLoaded` → `start()` → `bindEvents()`.
2. Нет токена — остаётся форма входа.
3. Есть токен — `API.me()` проверяет его, затем `enterApp(user)`: загружает `DATA`, восстанавливает `state`, рисует список чатов и нужный экран.
4. Токен не подошёл — `API.logout()` и снова форма входа.

`formatCode` сама расставляет дефисы в коде: `123456789` → `123-456-789`.

Выход (`logout`): стираем `state` и токен, перезагружаем страницу — так проще, чем чистить все экраны вручную.

### Экраны

`navigate(имя)` показывает секцию `#screen-имя` и вызывает нужную функцию:

| Экран | Функция | Что рисуется |
|---|---|---|
| `main` | `renderChatList`, `openChat` | список чатов, переписка, панель справа |
| `search` | `renderSearch` | фильтры и карточки людей |
| `clubs` | `renderClubs`, `renderClubPage`, `renderClubTab` | каталог или страница клуба |
| `profile` | `renderProfile` | фото, статус, «о себе», интересы, «Написать» |
| `settings` | `renderSettings` | профиль, уведомления, тема, приватность |
| `admin` | `renderAdmin` | обзор, каналы, пользователи, модерация, объявления |

### Чаты

- `renderChatFilters` — кнопки «Все / Канал / Группа…» над списком.
- `renderChatList` — список чатов с учётом фильтра и счётчиком непрочитанных.
- `openChat(id)` — заголовок, сообщения (`messagesHtml`), панель справа (`renderChatInfo`), отметка «прочитано» (`API.markRead`). В каналы студентам поле ввода не показывается.
- `sendMessage` — отправка, затем чат перерисовывается.
- `openDm(userId)` — находит или создаёт личный чат и открывает его.
- `showChat(open)` — на телефоне переключает «список чатов ↔ переписка» (класс `is-chat-open`, кнопка «‹» в шапке чата).
- `onServerEvent` — новые сообщения без обновления страницы: `API.listen` держит открытым поток `GET /api/events`, и при каждом событии открытый чат перерисовывается (`loadMessages`), а у остальных обновляются превью и счётчик непрочитанных. Если связь пропадала, после переподключения всё подтягивается заново (`resync`).
- Преподавателям фильтр «Группа» не показывается: чаты групп сервер им не отдаёт.

Если пока грузились сообщения, человек успел открыть другой чат, результат выбрасывается (`if (state.chatId !== chatId) return;`). Так старый чат не «перепрыгнет» поверх нового.

### Клубы

Вкладки «Все / Мои» фильтруют по `memberIds`. На странице клуба — «Участники» и «Чат клуба». Писать в чат клуба могут только участники.

### Настройки

- Переключатели (`data-setting`) сразу сохраняются (`toggleSetting` → `API.saveSetting`) и применяются (`applySettings`).
- Интересы копятся в `myInterests`, а на сервер уходят вместе с формой «Сохранить» (`saveProfile`).
- Тема — `setTheme`, хранится в `localStorage`.

### Админ-панель

Каждая вкладка — отдельная функция, которая возвращает HTML: `dashboardTab`, `channelsTab`, `usersTab`, `moderationTab`, `announcementsTab`. `renderAdmin` выбирает нужную и вставляет результат. Кнопку «Админ» видит только пользователь с `isAdmin`, но настоящая проверка — на сервере.

## 10. Сервер: `back/main.go`

Здесь:

1. **Открывается база** — `openDB("studnet.db")` (см. раздел 12).
2. **Регистрируются адреса** — каждой паре «метод + путь» назначается обработчик из `api.go`:
   ```go
   mux.HandleFunc("GET /api/chats/{id}/messages", route(true, messages))
   ```
   `{id}` — часть адреса, которую обработчик достаёт через `r.PathValue("id")`. `route(true, …)` — нужен вход, `adminOnly(…)` — только для администратора.
3. **Отдаются файлы сайта** — только папки `css/`, `js/`, `images/` и `index.html`. Папку `back/` (код и база) скачать нельзя. Список файлов в папке (`/images/`) не показывается — это делает `noFolderList`.
4. **Добавляются заголовки** к каждому ответу:
   - `securityHeaders` — заголовки защиты (CSP и другие, см. раздел 13);
   - `allowOtherSites` — CORS: разрешает запросы со страницы, открытой не этим сервером (Live Server, файл с диска).
5. **Запускается сервер** с тайм-аутами: если клиент шлёт запрос очень медленно, сервер не ждёт его вечно.

## 11. Сервер: `back/api.go` — все адреса API

### Как устроен обработчик

Каждый обработчик выглядит так:

```go
func имя(w http.ResponseWriter, r *http.Request, user map[string]any) error
```

- `user` — тот, кто вошёл (строка из таблицы `users` в виде «колонка → значение»);
- вернуть `nil` — всё хорошо; вернуть ошибку — человек получит «Ошибка сервера», а подробности уйдут в лог.

Обёртка `route` перед каждым обработчиком находит пользователя по токену: токен должен быть в таблице `sessions`, не просрочен, а пользователь — не заблокирован.

Помощники: `send` (ответить JSON-ом), `fail` (ответить ошибкой `{"error": "текст"}`), `ok` (ответить `{"ok": true}`), `readBody` (прочитать JSON из запроса, не больше 64 КБ), `readText`, `tooLong`, `isEmail`.

### Все адреса

| Метод и адрес | Кто может | Что делает |
|---|---|---|
| `POST /api/login` `{code}` | все | вход по коду. Ответ: `{token, user}`. После 5 ошибок с одного IP — пауза 1 минута |
| `POST /api/logout` | вошедший | удаляет токен, ставит «не в сети» |
| `GET /api/me` | вошедший | данные о себе |
| `POST /api/me` `{name, email, bio, interests}` | вошедший | сохранить профиль (с проверкой длины и почты) |
| `POST /api/settings` `{key, value}` | вошедший | включить/выключить настройку |
| `GET /api/data` | вошедший | все данные сайта (как `MOCK_DATA`). Чужие настройки и почта не отдаются |
| `GET /api/chats/{id}/messages` | участник чата | сообщения чата |
| `POST /api/chats/{id}/messages` `{text}` | участник чата | отправить сообщение (в каналы — только преподаватели) |
| `POST /api/chats/{id}/read` | участник чата | отметить чат прочитанным |
| `POST /api/dm` `{userId}` | вошедший | найти или создать личный чат |
| `POST /api/clubs/{id}/toggle` | вошедший | вступить в клуб / выйти |
| `GET /api/clubs/{id}/messages` | вошедший | сообщения чата клуба |
| `POST /api/clubs/{id}/messages` `{text}` | участник клуба | написать в чат клуба |
| `GET /api/events` | вошедший | поток новых сообщений (Server-Sent Events, `back/events.go`): ответ не закрывается, сервер дописывает в него `data: {...}` при каждом новом сообщении. Каждое событие получают только те, кто может видеть чат |
| `GET /api/admin/stats` | администратор | цифры для «Обзора» |
| `POST /api/admin/channels` `{name, description}` | администратор | создать канал |
| `POST /api/admin/channels/{id}` `{name, description}` | администратор | изменить канал |
| `GET /api/admin/reports` | администратор | список жалоб |
| `POST /api/admin/reports/{id}/dismiss` | администратор | отклонить жалобу |
| `POST /api/admin/users/{id}/block` `{blocked}` | администратор | заблокировать / разблокировать (администратора нельзя) |

«Участник чата» означает (функция `canSeeChat`): в личный чат пускают только двоих собеседников, в чат группы (`type: "group"`) — только студентов (преподаватели его не видят ни в списке, ни по прямому адресу), остальные чаты общие.

### Непрочитанные сообщения

Таблица `chat_reads` хранит, до какого сообщения человек дочитал каждый чат (`lastReadId`). Непрочитанные = чужие сообщения в чате с `id` больше `lastReadId`. Это считается одним SQL-запросом в `allData`.

## 12. Сервер: `back/db.go` и `back/schema.sql` — база данных

### Создание базы

`openDB` при запуске:

1. Открывает файл `studnet.db` (если файла нет, SQLite создаёт пустой).
2. Читает версию базы (`PRAGMA user_version`). Совпадает с `schemaVersion` — база готова.
3. Не совпадает (новая или устаревшая база) — удаляет файл и вызывает `createDB`:
   - выполняет `schema.sql` (создаёт таблицы);
   - читает `js/data.js`, вырезает JSON и раскладывает данные по таблицам функцией `insert`;
   - всё в одной **транзакции**: если что-то пошло не так, в базу не запишется ничего;
   - записывает новую версию.

Поменяли `schema.sql` — увеличьте `schemaVersion` в `db.go`, и база пересоздастся сама.

### Чтение

- `query(sql, параметры...)` — выполняет SELECT и возвращает список строк `[{колонка: значение}, ...]`. Такой список сразу превращается в JSON, поэтому отдельные структуры Go для каждой таблицы не нужны. Колонки с JSON-текстом (`interests`, `reactions`, `memberIds`) отдаются как настоящие списки.
- `queryOne(...)` — то же для одной строки (или `nil`, если ничего не нашлось).

### Таблицы

| Таблица | Что хранит |
|---|---|
| `users` | пользователи + их настройки (`notifyUnread`, `compact`, `showOnline`…), `isAdmin`, `blocked` |
| `access_codes` | код доступа → id пользователя |
| `sessions` | выданные токены: `token`, `userId`, `expiresAt` (до какого времени действует) |
| `study_groups`, `directions` | списки для фильтров |
| `chat_types` | типы чатов: подпись, `readonly` |
| `chats` | чаты; у личных — `ownerId` и `userId` |
| `messages` | сообщения чатов; `reactions` — JSON-список |
| `chat_reads` | до какого сообщения человек дочитал чат |
| `clubs`, `club_members` | клубы и кто в них состоит |
| `club_messages` | сообщения чатов клубов |
| `reports` | жалобы |

Названия колонок совпадают с полями в `data.js` (`lastMessage`, `userId`…). Поэтому данные переносятся без ручного сопоставления, а сайт получает их в том же виде, что и без сервера.

## 13. Безопасность

### 13.1. XSS (вставка вредного кода в страницу)

**Что это.** Человек пишет в сообщении, имени или «о себе» не текст, а HTML, например `<img src=x onerror="украсть токен">`. Если сайт вставит это в страницу как есть, браузер выполнит скрипт у каждого, кто увидит сообщение.

**Как защищаемся:**

1. **Экранирование (`esc` в `app.js`).** Каждое значение из данных перед вставкой в HTML проходит через `esc`, который заменяет `&`, `<`, `>`, `"`, `'` на `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;`. Браузер показывает их как обычные символы. Экранируется всё: тексты, имена, пути к картинкам, эмодзи, id и даже числа — чтобы не приходилось каждый раз думать «а может ли тут оказаться что-то опасное».
2. **`textContent` вместо `innerHTML`** там, где нужен просто текст (заголовок чата). `textContent` вообще не понимает HTML.
3. **Content-Security-Policy (CSP)** — заголовок, который сервер добавляет к каждому ответу (`main.go`). Он говорит браузеру: «скрипты — только из наших файлов, встроенные `<script>` и `onerror=` не выполнять». Это вторая стена: даже если где-то забыли `esc`, вредный скрипт не запустится. Именно поэтому скрипт из `<head>` вынесен в `js/theme.js`.
4. **JSON от сервера** — Go сам кодирует `<`, `>`, `&` как `<` и т.п., а заголовок `X-Content-Type-Options: nosniff` не даёт браузеру принять JSON за HTML.

Проверено: сообщение, «о себе» и интерес с текстом `<img src=x onerror=...>` и `<script>...</script>` показываются как обычный текст и ничего не выполняют.

### 13.2. SQL-инъекции

**Что это.** Если вклеить текст пользователя прямо в запрос — `"... WHERE code = '" + code + "'"` — то код `' OR 1=1 --` превратит запрос в «найди любого пользователя».

**Как защищаемся:**

1. **Все значения передаются параметрами** через знак `?`:
   ```go
   queryOne("SELECT ... WHERE a.code = ?", code)
   ```
   База получает текст запроса и значения раздельно, поэтому значение никогда не станет частью команды.
2. **Настройки (`/api/settings`)** — название колонки нельзя передать через `?`. Поэтому для каждой разрешённой настройки запрос написан целиком заранее (`settingQueries`). Чего нет в списке — то сохранить нельзя, в том числе `isAdmin`.
3. **Заполнение базы (`insert` в `db.go`)** — имена таблиц и колонок проверяются функцией `isSafeName`: только латинские буквы и `_`.

Проверено: вход с кодом `' OR 1=1 --`, адрес `/api/chats/2 OR 1=1/messages`, токен `x' OR '1'='1` и настройка `"isAdmin = 1, blocked"` — все отклоняются.

### 13.3. Подбор кода доступа

Код — всего 9 цифр. Без ограничений программа могла бы перебирать их тысячами в секунду. Теперь после **5 неудачных попыток** с одного IP-адреса вход с него закрывается на минуту (ответ 429 «Слишком много неверных попыток»). Удачный вход обнуляет счётчик. Код — в `api.go`, раздел «Защита от перебора кодов».

### 13.4. Токены и сессии

- Токен — 32 случайных байта из `crypto/rand` (криптографически стойкий генератор), угадать невозможно.
- Токен живёт **7 дней** (`expiresAt` в таблице `sessions`), потом нужно войти снова. Просроченные токены удаляются при каждом входе.
- Выход и блокировка удаляют токены из базы — они сразу перестают работать.
- Токен лежит в `sessionStorage`, а не в cookie. Поэтому чужой сайт не может отправить запрос «от имени» пользователя (CSRF), и разрешать CORS всем (`*`) здесь безопасно.

### 13.5. Права доступа

Всё, что прячется на сайте (кнопка «Админ», поле ввода в канале), **обязательно** проверяется и на сервере, потому что запрос можно отправить вручную:

- админ-адреса — `adminOnly` (только `isAdmin = 1`);
- писать в каналы — только преподаватели;
- личные чаты видят и читают только двое собеседников (`canSeeChat`);
- чаты групп видят только студенты, преподавателям они не отдаются (`canSeeChat`, условие в `allData`);
- мгновенные события (`/api/events`) получают только те, кому можно видеть чат; заблокированному поток сразу обрывается;
- писать в чат клуба — только участники;
- заблокированный пользователь не может войти, а его токены удалены;
- администратора заблокировать нельзя.

### 13.6. Приватность

`/api/data` отдаёт про **других** людей только то, что нужно для сайта:

- почту — только администратору (она нужна ему в таблице пользователей);
- личные настройки (уведомления, компактный режим и т.п.) — никому;
- если человек скрыл «в сети» или группу — вместо них отдаются «не в сети» и пустая строка.

### 13.7. Защита от слишком больших данных

- Сервер читает не больше 64 КБ из одного запроса (`http.MaxBytesReader`).
- Ограничения длины (одинаковые на сервере и в полях формы через `maxlength`):

  | Поле | Максимум символов |
  |---|---|
  | Имя | 50 |
  | Email | 100 (и проверка, что это похоже на почту) |
  | О себе | 500 |
  | Сообщение | 2000 |
  | Интерес | 30, всего не больше 10 |
  | Название канала | 60 |
  | Описание канала | 300 |

- Тайм-ауты сервера: медленный клиент не держит соединение вечно.

### 13.8. Другие заголовки и мелочи

| Что | Зачем |
|---|---|
| `X-Frame-Options: DENY` и `frame-ancestors 'none'` | сайт нельзя встроить в чужую страницу через `<iframe>` и обманом заставить нажать кнопку («кликджекинг») |
| `Referrer-Policy: no-referrer` | при переходе по ссылке другой сайт не узнает адрес нашей страницы |
| `noFolderList` | нельзя посмотреть список всех файлов в `/images/` |
| Статика только из `css/`, `js/`, `images/` | нельзя скачать `back/studnet.db` или код сервера |
| Ошибки сервера | человек видит только «Ошибка сервера», подробности — в логе |

### 13.9. Что осталось (честно)

Для учебного проекта этого достаточно, но в настоящем сайте стоило бы ещё:

- работать по **HTTPS** (сейчас всё идёт открытым текстом по HTTP);
- хранить в базе не сами токены и коды, а их хеши — тогда утечка файла базы не дала бы войти;
- запускать сервер только на `localhost` или за прокси, если его не нужно показывать в локальной сети;
- помнить, что режим без сервера (`data.js`) — только демонстрация: все данные и коды видны любому в исходном коде страницы.

## 15. Типичный путь клика

Пример: человек нажал «Написать» на карточке в поиске.

1. У кнопки атрибут `data-write="5"` (id Антона).
2. Общий обработчик кликов в `bindEvents` видит `data-write` и вызывает `openDm(5)`.
3. Чата с Антоном ещё нет — вызывается `API.openDm(5)`.
4. `api.js` отправляет `POST /api/dm {"userId": 5}` (или без сервера — `LOCAL.openDm(5)`).
5. Сервер (`openDm` в `api.go`) проверяет, что человек существует и разрешил сообщения, создаёт чат и возвращает его.
6. `navigate('main')` открывает экран чатов, `openChat(id)` рисует переписку.

Все действия устроены так же: **атрибут в HTML → обработчик → функция → `API` → сервер → снова `render…`**.

## 16. Что менять, если нужно доработать

- **Новый пользователь, чат, клуб** — только `js/data.js` (и удалить `back/studnet.db`, если сервер уже запускали).
- **Новый цвет или отступ** — `css/variables.css` или нужный css-файл.
- **Новая кнопка на экране** — разметка в `index.html` или в `render…` функции `app.js`, обработчик — в `bindEvents`.
- **Новое действие с данными:**
  1. метод в объекте `API` (`js/api.js`) и такой же в `LOCAL`;
  2. обработчик в `back/api.go` (с проверкой прав и длины полей!);
  3. строчка с адресом в `back/main.go`.
- **Новая колонка в базе** — `back/schema.sql` + увеличить `schemaVersion` в `back/db.go` + поле в `js/data.js`.
- **Выводите новые данные на экран?** Не забудьте `esc(...)`.
- **Пишете SQL-запрос?** Значения — только через `?`, никогда не склеивайте строки.
